# Adaptive Agent Lab 面试讲解稿

## 30 秒项目介绍

这是一个不依赖 LangChain 的小型 Agent 运行与评测框架。模型只负责决定下一步是调用
工具还是返回答案，`AgentRunner` 负责参数校验、工具执行、错误回传和最大步数控制。
系统把完整执行轨迹保存到 SQLite，并分别评测最终答案、工具选择、首次调用成功率、
错误恢复和延迟。我还实现了从独立历史数据库检索“失败后成功”的相似轨迹，并做了
隔离的 Memory A/B 实验。

## 一次任务如何运行

1. 用户任务进入 `AgentRunner`。
2. 模型返回 `Action`（工具名和参数）或 `FinalAnswer`。
3. `AgentRunner` 找到工具并调用 `tool.invoke(arguments)`。
4. `Tool.invoke` 按 JSON Schema 检查缺失参数、多余参数和参数类型。
5. 工具成功或失败的结果都转换成 observation，并写入 SQLite。
6. 工具失败属于可恢复的内层错误，模型可以读取错误并修改参数后重试。
7. 达到最终答案、最大步数或运行级异常后，系统写入对应的结束状态。

## 模型、AgentRunner 和工具的边界

- 模型不会直接执行 Python 函数，只提出调用意图。
- `AgentRunner` 是普通 Python 程序，是整个循环的调度器，不是另一个大模型。
- `Tool.invoke` 是工具执行入口，负责参数边界检查后才调用具体 handler。
- SQLite 不负责思考，只负责保存 run、step、action、observation、error 和 timing。

## 为什么不用 LangChain

这个项目的目标是理解并验证 Agent 的最小运行机制。自己实现状态循环后，可以准确控制
错误如何进入下一轮、轨迹如何保存、最大步数如何限制，以及不同指标如何计算。生产项目
可以使用框架，但仍然需要理解这些底层边界，才能定位错误发生在模型、工具还是调度层。

## Memory 是怎么实现的

Memory 不是重新训练模型。系统从历史 SQLite 数据库筛选“先调用失败、后来恢复成功”的
任务轨迹，对当前任务和历史任务分词，并用 token 集合重叠度检索相似记录。命中的失败
调用、错误和成功调用被压缩成示例，在模型第一次决策前加入上下文。检索事件本身也会
写入当前轨迹。

历史数据库和评测数据库必须分开，否则当前测试题的运行结果可能反过来成为自己的
Memory，造成数据泄漏，使评测结果虚高。

## 最重要的真实实验

OpenRouter smoke evaluation 曾出现：工具选择正确，但输出格式错误；轨迹还显示模型连续
尝试了三个 lookup 参数。根据 SQLite 轨迹，我们加强了 JSON Schema 描述、系统提示和
最大步数限制。单例回归从 3 次工具调用、2 次错误、39.4 秒改善到 1 次调用、0 次错误、
7.7 秒。这里只能称为回归案例，不能声称对所有任务都有相同比例的提升。

Memory A/B 实验中，control 和 treatment 都一次成功，说明存在 ceiling effect。Treatment
成功召回了 1 条历史恢复轨迹，因此证明 Memory 数据链路可用；但因为样本只有 1 个，
不能声称 Memory 提升了正确率或延迟。

## 常见追问

### 为什么工具错误不直接让整个任务失败？

因为参数错误通常可恢复。`AgentRunner` 把它记录为 observation，让模型看到具体错误并在
下一步纠正。未知工具名等运行级问题则由外层错误处理结束整个 run。

### 为什么既评测答案又评测工具选择？

只看答案会掩盖过程问题。模型可能碰巧答对，却选择了错误工具、产生多次失败调用，或者
没有使用要求的工具。拆分指标才能定位质量、成本和可靠性问题。

### `call_id` 和 `response_id` 有什么用？

`call_id` 把某次工具输出对应到准确的函数调用；`response_id` 用于继续同一次 Responses
API 对话。没有这些关联标识，多次调用时模型无法可靠判断某个输出属于哪次请求。

### 项目现在有什么局限？

词法 Memory 只能按词语重叠找相似任务；现有真实模型实验规模较小；SQLite 适合本地实验
而不是高并发服务；强制杀死进程仍需要 stale-run 清理策略。这些限制都应如实说明。
