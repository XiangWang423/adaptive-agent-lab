# Single-case trajectory memory A/B experiment

Date: 2026-08-15

This experiment checks whether a live OpenRouter model receives an isolated recovered trajectory
before solving a held-out task. It is a functional validation, not a statistically meaningful
performance claim.

## Setup

- Provider: OpenRouter
- Model: `openai/gpt-5-nano`
- Memory source: a controlled fault-injection run for the capital of Japan
- Historical failed call: `lookup({"key": "country:Japan"})`
- Historical recovered call: `lookup({"key": "capital:Japan"})`
- Held-out task: choose the lookup key for the capital of France
- Historical and evaluation SQLite databases were separate
- Retrieved task similarity: `0.476` with a minimum threshold of `0.2`

The memory contained tool actions and an error, but not the held-out answer `Paris`.

## Results

| Metric | Control | Memory treatment |
| --- | ---: | ---: |
| Cases | 1 | 1 |
| Success rate | 100% | 100% |
| First-tool-call success | 100% | 100% |
| Tool errors | 0 | 0 |
| Average tool calls | 1 | 1 |
| Average steps | 2 | 2 |
| Cases with memory recall | 0 | 1 |
| Memory recall rate | n/a | 100% |
| Latency | 9,374.963 ms | 6,956.233 ms |

The treatment was 2,418.730 ms (25.8%) faster in this observation. That difference must not be
attributed to memory because the experiment used one case, had no repetitions, and did not control
provider or network variance.

## Interpretation

The experiment verifies the complete memory path:

1. retrieve a similar recovery from an isolated SQLite database;
2. inject one failed-call/successful-call lesson before the first model decision;
3. record the recall in the evaluation trajectory;
4. complete the held-out task successfully.

It does not demonstrate an accuracy or tool-efficiency improvement. The control already solved the
case with one successful tool call, so the test had a ceiling effect. A larger held-out suite with
repeated runs is required before claiming a quality, cost, or latency improvement.

## Reliability finding

The first treatment attempt was interrupted after a successful tool call when connectivity was
lost. The process interruption left the SQLite run marked as `running`. A follow-up fix records
`KeyboardInterrupt` and `SystemExit` runs as `interrupted` before re-raising them to the terminal.
Hard process termination still requires a future stale-run recovery policy.
